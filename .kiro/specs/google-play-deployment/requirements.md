# Requirements Document

## Introduction

This feature covers the complete setup for building, signing, and deploying the Kinetic-Jewelry Android app to the Google Play Store. It includes changing the application identifier and namespace to the production domain (`ch.rhosys.lyra`), renaming all source packages accordingly, generating a KMS-encrypted signing keystore, configuring Gradle for release signing via CI decryption, creating GitLab CI pipelines (`.gitlab-ci.yml`), automated deployment to the Play Store Internal Testing track via GCP Workload Identity Federation, and preparing the project for Play Store submission.

The project lives at `rhosys/rapid/kinetic-jewelry` on GitLab.

## Glossary

- **Build_System**: The Gradle build toolchain (Kotlin DSL) that compiles, packages, and signs the Android application
- **CI_Pipeline**: The GitLab CI pipeline (`.gitlab-ci.yml`) that validates code quality on every push and merge request
- **Build_Pipeline**: The GitLab CI jobs (`build-release`, `build-debug`) that produce debug APKs on merge requests and signed release AABs on pushes to main
- **Deploy_Pipeline**: The GitLab CI job (`deploy-release`) that uploads the signed AAB to the Google Play Internal Testing track via GCP Workload Identity Federation
- **Signing_Configuration**: The CI job steps that decrypt the keystore password via KMS and pass signing credentials to Gradle as command-line properties
- **Keystore**: A PKCS12 file containing the RSA 4096-bit private key used to sign release builds, generated by the `generate-android-keystore` tool and encrypted with AWS KMS
- **Keystore_JSON**: The file `deployment/android-upload-signing.json` committed to the repository, containing the base64-encoded keystore and the KMS-encrypted password ciphertext
- **AAB**: Android App Bundle — the distribution format required by Google Play Store
- **APK**: Android Package — the installable format used for debug testing
- **R8**: The Android code shrinker and obfuscator that runs during release builds (replaces ProGuard)
- **Application_ID**: The unique identifier (`ch.rhosys.lyra`) that identifies the app on Google Play and on devices
- **Namespace**: The Gradle `namespace` property (`ch.rhosys.lyra`) that determines the generated R class package and serves as the base package for AndroidManifest relative class references
- **OIDC_Role**: The AWS IAM role (`GitLabRunnerRole`) assumed by the GitLab CI runner via OpenID Connect federation, granting `kms:Decrypt` permission on `alias/deployment-encryption-key`
- **GCP_WIF**: GCP Workload Identity Federation — the mechanism by which the GitLab CI `deploy-release` job authenticates to Google Cloud as `gitlab-play-store@rhosys-apps.iam.gserviceaccount.com` to publish AABs to the Play Store, using the `gitlab-oidc` pool and `gitlab-com` provider in GCP project `rhosys-apps`
- **Deploy_Script**: The TypeScript script at `deployment/deploy-play-store.ts` that uses `@googleapis/androidpublisher` to upload the signed AAB to the Google Play Internal Testing track for package `ch.rhosys.lyra`
- **KMS_Decryption**: The process of decrypting ciphertext at build time using `aws kms decrypt` via the CI runner's OIDC-assumed IAM role; plaintext exists only in memory for the duration of the job
- **Setup_Script**: The shell script at `scripts/setup.sh` that installs Java 17, Android SDK command-line tools, required SDK components, configures environment variables, and validates KVM acceleration
- **Emulator_Scripts**: The shell scripts at `scripts/emulator-create.sh`, `scripts/emulator-start.sh`, and `scripts/emulator-delete.sh` that manage the development Android Virtual Device (WorkspaceAVD)
- **Git_Hooks**: The Husky-managed git hooks (commit-msg and pre-commit) that enforce commit message quality and run linting on staged files before commit
- **Lint_Staged**: The lint-staged configuration that runs ktlint on staged `*.kt` files during the pre-commit hook
- **Unified_Check**: The single Gradle command or script that runs compilation, lint, and unit tests in sequence as a pre-push quality gate
- **Setup_Documentation**: The `docs/SETUP.md` file documenting prerequisites, installation, emulator setup, daily workflow, available commands, and troubleshooting

## Requirements

### Requirement 1: Application Identity Configuration

**User Story:** As a developer, I want the application ID and namespace both set to `ch.rhosys.lyra`, so that the app uses a single consistent identity across Google Play, the build system, and source code.

#### Acceptance Criteria

1. THE Build_System SHALL use `ch.rhosys.lyra` as the applicationId in the `defaultConfig` block
2. THE Build_System SHALL use `ch.rhosys.lyra` as the namespace in the `android` block
3. THE Build_System SHALL append `.debug` to the applicationId for debug builds, resulting in `ch.rhosys.lyra.debug`
4. WHEN a release build is produced, THE Build_System SHALL embed `ch.rhosys.lyra` as the package attribute in the output APK/AAB manifest
5. WHEN a debug build is produced, THE Build_System SHALL embed `ch.rhosys.lyra.debug` as the package attribute in the output APK manifest
6. THE Build_System SHALL generate the R class under the `ch.rhosys.lyra` package

### Requirement 2: Source Package Rename

**User Story:** As a developer, I want all source files moved from `com.rhosys.kineticjewelry` to `ch.rhosys.lyra`, so that the source package matches the namespace and no references to the old package remain.

#### Acceptance Criteria

1. THE Build_System SHALL place all main source files under the directory path `app/src/main/java/ch/rhosys/lyra/` instead of `app/src/main/java/com/rhosys/kineticjewelry/`
2. THE Build_System SHALL place all debug source files under the directory path `app/src/debug/java/ch/rhosys/lyra/` instead of `app/src/debug/java/com/rhosys/kineticjewelry/`
3. THE Build_System SHALL update all `package` declarations in Kotlin source files from `package com.rhosys.kineticjewelry` (and subpackages) to `package ch.rhosys.lyra` (and corresponding subpackages)
4. THE Build_System SHALL update all `import` statements referencing `com.rhosys.kineticjewelry` (and subpackages) to reference `ch.rhosys.lyra` (and corresponding subpackages)
5. THE Build_System SHALL update all R class imports from `com.rhosys.kineticjewelry.R` to `ch.rhosys.lyra.R`
6. WHEN the source package rename is complete, THE Build_System SHALL compile without errors using `./gradlew compileDebugKotlin`
7. THE Build_System SHALL preserve all relative class references in AndroidManifest.xml (e.g., `.KineticJewelryApp`, `.MainActivity`, `.service.KineticNotificationListenerService`) without modification, since they resolve relative to the namespace

### Requirement 3: Signing Keystore Generation

**User Story:** As a developer, I want a signing keystore generated and encrypted with KMS, so that signing credentials are securely stored in the repository without exposing plaintext secrets.

#### Acceptance Criteria

1. WHEN the `generate-android-keystore` tool is run with `--alias lyra`, THE Build_System SHALL write a JSON object to stdout containing a `keystore` field and a `passwordCiphertext` field
2. THE Keystore_JSON `keystore` field SHALL contain the base64-encoded PKCS12 keystore (password-protected, not KMS-encrypted)
3. THE Keystore_JSON `passwordCiphertext` field SHALL contain the base64-encoded KMS ciphertext of the keystore password, encrypted using the `alias/deployment-encryption-key` key in `eu-west-1`
4. THE Build_System SHALL use RSA 4096-bit keys with 10950-day validity (30 years) and PKCS12 store type
5. THE Build_System SHALL use DN `CN=rhosys.ch, O=Rhosys AG, OU=Mobile, L=Unknown, ST=Unknown, C=CH`
6. THE Build_System SHALL generate a cryptographically random password of 32 bytes encoded as a base64url string (no `+`, `/`, or `=` characters)
7. WHEN keystore generation completes or fails, THE Build_System SHALL delete the temporary plaintext keystore file from disk before returning
8. IF the `--alias` argument is missing, THEN THE Build_System SHALL exit with a non-zero exit code and print a usage message to stderr without producing JSON output
9. THE Build_System SHALL commit the generated JSON output to `deployment/android-upload-signing.json` in the repository

### Requirement 4: Gradle Signing Configuration

**User Story:** As a developer, I want Gradle configured to accept signing credentials as command-line properties, so that CI can produce signed AABs after decrypting the keystore from the repository.

#### Acceptance Criteria

1. WHEN `-Pandroid.injected.signing.store.file`, `-Pandroid.injected.signing.store.password`, `-Pandroid.injected.signing.key.alias`, and `-Pandroid.injected.signing.key.password` properties are all provided on the Gradle command line, THE Build_System SHALL sign the release build using those credentials
2. IF the `android.injected.signing` properties are not provided, THEN THE Build_System SHALL skip signing configuration and complete the build with exit code 0, producing an unsigned output
3. THE Signing_Configuration SHALL read `deployment/android-upload-signing.json` from the repository, extract the `keystore` field, and decode it from base64 to a temporary PKCS12 file
4. THE Signing_Configuration SHALL decrypt the `passwordCiphertext` field from `deployment/android-upload-signing.json` using `aws kms decrypt` via the CI runner's OIDC_Role
5. THE Signing_Configuration SHALL pass the decoded keystore path and decrypted password to Gradle via `-Pandroid.injected.signing.store.file`, `-Pandroid.injected.signing.store.password`, `-Pandroid.injected.signing.key.alias=lyra`, and `-Pandroid.injected.signing.key.password` properties
6. WHEN signing is configured and the release build succeeds, THE Build_System SHALL produce a signed AAB at `app/build/outputs/bundle/release/app-release.aab` that passes `jarsigner -verify` validation
7. IF the decoded keystore file is invalid or the decrypted password does not match the keystore, THEN THE Build_System SHALL fail the build with a non-zero exit code and an error message indicating the signing failure

### Requirement 5: CI Pipeline — Code Quality

**User Story:** As a developer, I want a CI pipeline that validates compilation, lint, and tests on every push, so that code quality issues are caught before merging.

#### Acceptance Criteria

1. WHEN code is pushed to any branch or a merge request is opened, THE CI_Pipeline SHALL run compilation checks using `./gradlew compileDebugKotlin`
2. WHEN code is pushed to any branch or a merge request is opened, THE CI_Pipeline SHALL run Android Lint using `./gradlew lintDebug`
3. WHEN code is pushed to any branch or a merge request is opened, THE CI_Pipeline SHALL run unit tests using `./gradlew testDebugUnitTest`
4. THE CI_Pipeline SHALL execute compilation, lint, and test as jobs in the `validate` and `test` stages within `.gitlab-ci.yml`
5. IF any CI job fails, THEN THE CI_Pipeline SHALL report a failing pipeline status on the associated merge request, preventing merge when pipeline success is required
6. THE CI_Pipeline SHALL cache Gradle dependencies and wrapper using a branch-keyed cache strategy
7. THE CI_Pipeline SHALL use a Docker image with Java 17 and Android SDK (or a base image with Java 17 for compile/lint/test jobs that only need the Gradle wrapper to download the SDK)

### Requirement 6: Build Pipeline — Debug and Release Artifacts

**User Story:** As a developer, I want build jobs that produce debug APKs on merge requests and signed release AABs on main, so that I can test MRs and deploy releases from CI.

#### Acceptance Criteria

1. WHEN a merge request is opened, THE Build_Pipeline `build-debug` job SHALL build an unsigned debug APK using `./gradlew assembleDebug` (manual trigger)
2. WHEN a merge request is opened, THE Build_Pipeline `build-debug` job SHALL upload the debug APK as a CI artifact with 7-day retention
3. WHEN code is pushed to the main branch, THE Build_Pipeline `build-release` job (manual trigger) SHALL configure AWS OIDC credentials by writing the `GITLAB_OIDC_TOKEN` to `$AWS_WEB_IDENTITY_TOKEN_FILE` and setting `AWS_ROLE_ARN` to `arn:aws:iam::${AWS_ACCOUNT_ID}:role/GitLabRunnerRole`
4. WHEN code is pushed to the main branch, THE Build_Pipeline `build-release` job SHALL extract the `keystore` field from `deployment/android-upload-signing.json`, decode it from base64, and write it to a temporary file
5. WHEN code is pushed to the main branch, THE Build_Pipeline `build-release` job SHALL decrypt the `passwordCiphertext` field from `deployment/android-upload-signing.json` using `aws kms decrypt --region eu-west-1` via the OIDC_Role
6. WHEN code is pushed to the main branch, THE Build_Pipeline `build-release` job SHALL build a signed release AAB using `./gradlew bundleRelease` with `-Pandroid.injected.signing.store.file`, `-Pandroid.injected.signing.store.password`, `-Pandroid.injected.signing.key.alias=lyra`, and `-Pandroid.injected.signing.key.password` properties
7. WHEN code is pushed to the main branch, THE Build_Pipeline `build-release` job SHALL upload the signed AAB as a CI artifact with 30-day retention
8. THE Build_Pipeline SHALL use a lean Android SDK Docker image with JDK 17 (e.g., `cimg/android:2024.01` or equivalent) for build jobs — not the React Native community image
9. IF the KMS decryption fails or the OIDC role assumption fails, THEN THE Build_Pipeline SHALL fail the job with an error indicating the decryption or role assumption failure
10. THE CI_Pipeline SHALL require only one non-secret CI/CD variable: `AWS_ACCOUNT_ID` (value `981461567584`), configured in GitLab project settings

### Requirement 7: Play Store Deployment

**User Story:** As a developer, I want the signed AAB automatically uploaded to the Play Store Internal Testing track after a successful release build, so that testers receive new builds without manual intervention.

#### Acceptance Criteria

1. WHEN the `build-release` job completes successfully, THE Deploy_Pipeline `deploy-release` job SHALL run automatically (not manual) on the main branch
2. THE Deploy_Pipeline SHALL authenticate to GCP by exchanging the GitLab OIDC token for GCP credentials using Workload Identity Federation with audience `//iam.googleapis.com/projects/454629444494/locations/global/workloadIdentityPools/gitlab-oidc/providers/gitlab-com`
3. THE Deploy_Pipeline SHALL impersonate the service account `gitlab-play-store@rhosys-apps.iam.gserviceaccount.com` to obtain Play Store API access
4. THE Deploy_Pipeline SHALL execute the Deploy_Script at `deployment/deploy-play-store.ts` to upload the AAB to the `internal` track for package `ch.rhosys.lyra`
5. THE Deploy_Script SHALL use `@googleapis/androidpublisher` to create an edit, upload the AAB bundle, assign it to the `internal` track, and commit the edit
6. IF the app is in draft state on Play Console, THEN THE Deploy_Script SHALL retry the release with `draft` status and print a message indicating manual promotion is required
7. IF the Play Store API returns a 404 (package not found), THEN THE Deploy_Script SHALL exit with a non-zero code and print instructions for creating the app and uploading the first AAB manually via Play Console
8. THE Deploy_Pipeline SHALL use the `node:24` image and install dependencies via `npm ci` to execute the TypeScript deploy script

### Requirement 8: GCP Workload Identity Federation Infrastructure

**User Story:** As a developer, I want the GCP WIF binding for Kinetic-Jewelry configured in the shared infrastructure repo, so that the deploy job can authenticate to GCP without stored credentials.

#### Acceptance Criteria

1. THE GCP_WIF infrastructure SHALL include a `google_service_account_iam_member` resource in `_rhosys-apps-infra/gcp/main.tf` binding the `gitlab-play-store` service account to the `rhosys/rapid/kinetic-jewelry` project path
2. THE GCP_WIF binding SHALL use role `roles/iam.workloadIdentityUser` on the `gitlab-play-store` service account
3. THE GCP_WIF binding SHALL use member `principalSet://iam.googleapis.com/${google_iam_workload_identity_pool.gitlab.name}/attribute.project_path/rhosys/rapid/kinetic-jewelry`
4. THE GCP_WIF binding SHALL reuse the existing `google_iam_workload_identity_pool.gitlab` pool and `google_service_account.play_store` service account already defined for cycle-tracker

### Requirement 9: R8 Code Shrinking for Release Builds

**User Story:** As a developer, I want R8 properly configured for release builds, so that the app is optimized and obfuscated for production.

#### Acceptance Criteria

1. WHILE building a release variant, THE Build_System SHALL enable code minification via R8 by setting `isMinifyEnabled = true` in the release build type
2. WHILE building a release variant, THE Build_System SHALL reference `proguard-android-optimize.txt` as the default optimization rules file in the proguardFiles configuration
3. WHILE building a release variant, THE Build_System SHALL apply project-specific keep rules that preserve Room database classes (entities, DAOs, and RoomDatabase subclasses under `ch.rhosys.lyra.data.local.db`), Hilt-annotated classes (`@HiltAndroidApp`, `@AndroidEntryPoint`), and Room type converters
4. THE Build_System SHALL reference `ch.rhosys.lyra` in all ProGuard/R8 keep rules that specify package paths
5. WHEN a release variant build completes, THE Build_System SHALL produce an APK or AAB without R8-related compilation errors, confirming that keep rules are sufficient to preserve all classes accessed via reflection

### Requirement 10: Version Management

**User Story:** As a developer, I want a clear versioning scheme, so that each release uploaded to Google Play has a unique version code and meaningful version name.

#### Acceptance Criteria

1. THE Build_System SHALL define `versionCode` as a positive integer starting at 1 that is strictly incremented by exactly 1 with each Play Store upload
2. THE Build_System SHALL define `versionName` following semantic versioning in the format MAJOR.MINOR.PATCH where each segment is a non-negative integer (e.g., "1.0.0", "1.2.3")
3. THE Build_System SHALL set the initial release to versionCode 1 and versionName "1.0.0"
4. WHEN a new release is prepared, THE Build_System SHALL ensure the new `versionCode` is greater than the `versionCode` of any previously uploaded build
5. IF `versionName` does not match the pattern of three dot-separated non-negative integers (MAJOR.MINOR.PATCH), THEN THE Build_System SHALL fail the build with an error indicating an invalid version name format

### Requirement 11: Deployment Documentation

**User Story:** As a developer, I want documentation covering the full signing and deployment process, so that future developers can understand and maintain the pipeline.

#### Acceptance Criteria

1. THE Build_System SHALL include a `docs/SIGNING.md` file containing sections for: invoking the `generate-android-keystore` tool with the `lyra` alias, the structure of `deployment/android-upload-signing.json` committed to the repo, the KMS decryption pattern used in CI to extract the keystore and password at build time, and the required OIDC_Role configuration (`kms:Decrypt` permission on `alias/deployment-encryption-key` in `eu-west-1`)
2. THE Build_System SHALL include a `docs/CI_CD.md` file containing sections for: the GitLab CI pipeline stages and jobs (validate, test, build, deploy), the `build-release` job trigger conditions (manual, main only), the `deploy-release` job (automatic after build-release), artifact retention periods, required runner environment, AWS OIDC configuration, and GCP WIF configuration for Play Store deployment
3. THE Build_System SHALL include in `docs/CI_CD.md` a section documenting the automated deployment to the Play Store Internal Testing track via the `deploy-release` job, including the GCP authentication flow and the deploy script
4. THE Build_System SHALL include in `docs/SIGNING.md` a section documenting the process for rotating the upload signing key via Google Play Console's Play App Signing, including when rotation is necessary and the steps to enroll a new upload key

### Requirement 12: Developer Setup Script

**User Story:** As a developer, I want a single setup script that installs all build prerequisites, so that I can go from a fresh clone to a working build environment without manual steps.

#### Acceptance Criteria

1. THE Setup_Script SHALL verify that Java 17 is installed and install it via `apt-get` on Linux or `brew` on macOS if missing
2. THE Setup_Script SHALL download and install Android SDK command-line tools to `$ANDROID_HOME/cmdline-tools/latest/` if not already present
3. WHEN the Android SDK command-line tools are available, THE Setup_Script SHALL install the SDK components `platform-tools`, `build-tools;35.0.0`, and `platforms;android-35` via `sdkmanager`
4. THE Setup_Script SHALL accept all Android SDK licenses non-interactively via `yes | sdkmanager --licenses`
5. THE Setup_Script SHALL write `ANDROID_HOME` and the SDK tool paths to the shell profile files (`.bashrc`, `.zshrc`, `.profile`) using a unique marker block to prevent duplicate entries
6. WHILE running on Linux, THE Setup_Script SHALL validate KVM availability by checking `/dev/kvm` and install `qemu-kvm` if the device is missing but the CPU supports hardware virtualisation
7. IF the CPU does not support hardware virtualisation (no `vmx` or `svm` flags in `/proc/cpuinfo`), THEN THE Setup_Script SHALL print a warning indicating that BIOS/UEFI virtualisation must be enabled
8. THE Setup_Script SHALL be executable at `scripts/setup.sh` and exit with a non-zero code if any critical step fails
9. THE Setup_Script SHALL print a summary of next steps upon successful completion, including restarting the terminal and running `scripts/emulator-create.sh`

### Requirement 13: Emulator Scripts

**User Story:** As a developer, I want scripts to create, start, and delete a development emulator, so that I can test the app locally without Android Studio.

#### Acceptance Criteria

1. WHEN `scripts/emulator-create.sh` is executed, THE Emulator_Scripts SHALL download the system image `system-images;android-35;google_apis;x86_64` via `sdkmanager` if not already installed
2. WHEN `scripts/emulator-create.sh` is executed, THE Emulator_Scripts SHALL create an AVD named `WorkspaceAVD` using the Pixel 7 device profile
3. IF the AVD `WorkspaceAVD` already exists, THEN `scripts/emulator-create.sh` SHALL print a message indicating the AVD exists and exit with code 0 without recreating it
4. WHEN `scripts/emulator-start.sh` is executed, THE Emulator_Scripts SHALL start the `WorkspaceAVD` emulator in the foreground using `$ANDROID_HOME/emulator/emulator -avd WorkspaceAVD -no-snapshot-load`
5. IF the AVD `WorkspaceAVD` does not exist when `scripts/emulator-start.sh` is run, THEN THE Emulator_Scripts SHALL print an error directing the user to run `scripts/emulator-create.sh` and exit with a non-zero code
6. WHEN `scripts/emulator-delete.sh` is executed, THE Emulator_Scripts SHALL delete the AVD named `WorkspaceAVD` using `avdmanager delete avd --name WorkspaceAVD`
7. THE Emulator_Scripts SHALL require `ANDROID_HOME` to be set and the SDK to be installed, exiting with a non-zero code and an error message if the SDK is not found

### Requirement 14: Git Hooks (Husky)

**User Story:** As a developer, I want git hooks that enforce commit message quality and run linting on staged files, so that code quality is maintained at the commit level.

#### Acceptance Criteria

1. WHEN a commit is created, THE Git_Hooks commit-msg hook SHALL reject the commit with a non-zero exit code if the commit message is shorter than 20 characters
2. WHEN a commit is rejected for message length, THE Git_Hooks commit-msg hook SHALL print an error message instructing the developer to explain WHY the change was made
3. WHEN a commit is created, THE Git_Hooks pre-commit hook SHALL execute lint-staged to run ktlint on staged `*.kt` files
4. THE Git_Hooks SHALL be managed by Husky and activated automatically when dependencies are installed via `npm install` (the `prepare` script)
5. IF ktlint reports errors on staged files during pre-commit, THEN THE Git_Hooks SHALL reject the commit with a non-zero exit code and display the lint errors

### Requirement 15: Lint-Staged Configuration

**User Story:** As a developer, I want staged Kotlin files automatically linted before commit, so that formatting and style issues are caught before they enter the repository.

#### Acceptance Criteria

1. WHEN a commit is created, THE Lint_Staged configuration SHALL run ktlint on all staged files matching the pattern `*.kt`
2. THE Lint_Staged configuration SHALL be defined in `package.json` under the `lint-staged` key
3. IF ktlint finds fixable formatting issues, THEN THE Lint_Staged configuration SHALL apply fixes automatically and re-stage the corrected files
4. THE Lint_Staged configuration SHALL require ktlint to be available either as a standalone binary installed by the setup script or via the ktlint Gradle plugin

### Requirement 16: .gitignore Hardening

**User Story:** As a developer, I want signing-related file patterns excluded from version control, so that plaintext keystores and signing keys are never accidentally committed.

#### Acceptance Criteria

1. THE Build_System SHALL include `*.jks` in `.gitignore` to exclude Java KeyStore files
2. THE Build_System SHALL include `*.p12` in `.gitignore` to exclude PKCS12 keystore files
3. THE Build_System SHALL include `*.key` in `.gitignore` to exclude private key files
4. THE Build_System SHALL include `*.mobileprovision` in `.gitignore` to exclude iOS provisioning profiles
5. THE Build_System SHALL include `*.keystore` in `.gitignore` to exclude Android keystore files
6. THE Build_System SHALL include `/local.properties` in `.gitignore` to exclude local SDK path configuration
7. THE Build_System SHALL preserve all existing `.gitignore` entries (including `*.apk` and `*.aab`) when adding the new patterns

### Requirement 17: Unified Check Command

**User Story:** As a developer, I want a single command that runs compilation, lint, and tests in sequence, so that I can validate the entire project before pushing.

#### Acceptance Criteria

1. THE Unified_Check SHALL execute `./gradlew compileDebugKotlin lintDebug testDebugUnitTest` as a single Gradle invocation
2. IF any task in the Unified_Check fails, THEN THE Unified_Check SHALL stop execution and exit with a non-zero code indicating which task failed
3. THE Unified_Check SHALL be runnable via `./gradlew check` or a wrapper script at `scripts/check.sh`
4. THE Unified_Check SHALL be documented in `docs/SETUP.md` as the command to run before pushing

### Requirement 18: Local Build Scripts

#### Acceptance Criteria

1. THE Build_System SHALL support building a debug APK via `./gradlew assembleDebug`, producing output at `app/build/outputs/apk/debug/app-debug.apk`
2. THE Build_System SHALL support building an unsigned release AAB via `./gradlew bundleRelease` when no signing properties are provided

WHEN signing properties are provided via `-Pandroid.injected.signing.store.file`, `-Pandroid.injected.signing.store.password`, `-Pandroid.injected.signing.key.alias=lyra`, and `-Pandroid.injected.signing.key.password`, THE Build_System SHALL produce a signed release AAB at `app/build/outputs/bundle/release/app-release.aab`

### Requirement 19: Setup Documentation

**User Story:** As a developer, I want a comprehensive setup guide, so that new contributors can configure their environment and start developing without tribal knowledge.

#### Acceptance Criteria

1. THE Setup_Documentation SHALL include a prerequisites section listing Java 17 and Android SDK as requirements, with manual installation instructions as fallback
2. THE Setup_Documentation SHALL include instructions for running `scripts/setup.sh` and what it installs automatically
3. THE Setup_Documentation SHALL include instructions for emulator setup via `scripts/emulator-create.sh` and `scripts/emulator-start.sh`

7. THE Setup_Documentation SHALL be located at `docs/SETUP.md` in the repository root
